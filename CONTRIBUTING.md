# Contributing to idstack

## Quick start

1. Fork the repo and clone your fork
2. Create a branch: `git checkout -b my-skill`
3. Add your skill (see below)
4. Run `bin/idstack-gen-skills` to generate the skill files from your template
5. Run `./setup` to register it
6. Run the test suite (see [Testing](#testing)) to verify
7. Submit a PR

## How skills work

One directory, one source file, one generated file per target:

```
skills/your-skill/
├── SKILL.md.tmpl  # Source — this is the file you edit
└── SKILL.md       # Generated by bin/idstack-gen-skills — do not edit
```

That's the entire skill. No backend, no config files, no registration step beyond `./setup`. A new skill does change the skill count, so update every hard-coded skill list and count: smoke-test finds some of them, and `git grep -nE '(^|[^0-9])12 skills'` finds the rest. Edit the `.tmpl` and regenerate — a hand-edit to `SKILL.md` is overwritten on the next `bin/idstack-gen-skills` run, and the smoke test fails on the drift in the meantime.

### SKILL.md structure

**1. YAML frontmatter:**

```yaml
---
name: your-skill
description: |
  What this skill does, in 2-3 lines. (idstack)
allowed-tools:
  - Bash
  - Read
  - Write
  - Edit
  - Glob
  - Grep
  - AskUserQuestion
---
```

The bare `name` field becomes the slash-command suffix: `name: course-import` is invoked as `/idstack:course-import`. The installed plugin handles the `idstack:` namespace; do not prefix the name yourself.

**2. `{{PREAMBLE}}` placeholder** — this is replaced by `bin/idstack-gen-skills` with the shared preamble (writing standard, manifest check, context recovery).

**3. Skill implementation** — the rest of the file is Markdown that defines the skill's workflow, decision trees, and outputs.

**4. `{{MANIFEST_SCHEMA}}` placeholder (optional)** — replaced with `templates/manifest-schema.md`. Only `needs-analysis` and `course-import` use it.

**5. `{{IDSTACK_RESOLVE}}` placeholder** — replaced with `templates/snippets/idstack-resolve.sh`. Put this at the top of **every** bash block that calls `$_IDSTACK/bin/...`, not just the first. Bash blocks run in separate shells, so a value derived in an earlier block isn't there in a later one. Skipping it is how `learn` and `course-export` ended up pointing `bin/` calls at a nonexistent directory for marketplace installs.

**6. Timeline logging** — at the end, a section that logs the session to `.idstack/timeline.jsonl` with skill-specific fields. Not in `learn` or `start`: neither writes a timeline event.

**7. Writing standard check** — after each file that the skill writes for a person, a bash block runs `"$_IDSTACK/bin/idstack-ste-check"` on that file. `test/smoke-test.sh` fails if a skill template does not have exactly the number of check steps that the smoke test sets for it. When you add or remove a check step, update that number. A skill that starts a sub-agent puts a copy of the preamble's "Writing Standard (ASD-STE100)" section in the sub-agent prompt.

### Template system

Skills use a template system to share common preamble code. Edit `skills/{skill}/SKILL.md.tmpl`, not `SKILL.md` directly. The generated `SKILL.md` files have an `<!-- AUTO-GENERATED -->` header.

After editing a `.tmpl` file, `templates/preamble.md`, `templates/manifest-schema.md`, or `templates/snippets/idstack-resolve.sh`, regenerate:

```bash
bin/idstack-gen-skills            # write the regenerated files
bin/idstack-gen-skills --dry-run  # check only — exits non-zero if anything is stale
```

Commit the regenerated files in the same commit as the template change. The smoke test includes a freshness check that fails if any `SKILL.md` is stale.

### Embedded Python must run on 3.9

Any Python embedded in `templates/preamble.md` or a skill body has to parse on Python 3.9 — that is what macOS ships, and it is the interpreter most designers will hit. An f-string reusing a quote inside its replacement field is legal from 3.12 (PEP 701) and a SyntaxError before it, which is exactly how context recovery stayed silently broken for several releases. The preamble's Context Recovery calls `bin/idstack-status --context`, and `test/test-preamble-python.sh` runs that block on the local python3. CI runs it on 3.9 and 3.12.

### Shared libraries

Logic used by more than one script — or worth a unit test — belongs in `bin/lib/`, loaded by its callers rather than copy-pasted:

- `bin/lib/plugin-status.sh` — parses `claude plugin list` down to idstack's own entry
- `bin/lib/citations.py` — parses `[Code-N] [Tn]` citations and the tiers in `evidence/references.md`. Imported by `bin/idstack-report-section` and `test/check-citation-tiers.py`

Point the test at the shipped file, never at a copy of the logic. The version classifier drifted across three PRs while a mirrored copy inside its own test kept passing green.

## The dual-output contract

Every skill that produces findings writes **both**:

1. **JSON section** in `.idstack/project.json` — system state for downstream skills, the pipeline orchestrator, and `bin/idstack-status`.
2. **Markdown report** at `.idstack/exports/<course-slug>/<skill>.md` — the human view. Follow the skeleton in `templates/report.md.tmpl` and the content contract in `templates/report-format.md`: observation → evidence → why-it-matters → recommendation, with severity (`critical|warning|info`) and evidence tier (`T1`–`T5`) on every finding. The skill writes the relative path back into its section's `report_path` field and gives the user that relative path as the link to the report.

Build the report one section at a time with the "Step Review" in `templates/preamble.md`. After each step, `bin/idstack-report-section` checks the step's table (`ID` first, `Justification | Evidence` last). Then it adds the table to the report at once, as a draft section. `init` starts the report, and `check` and `append` add each draft. `approve` removes the draft mark when the user approves. `finish` fails while a draft or a placeholder remains. When a skill stops early, `finish --stopped` writes a note in each reserved score section that has no data. The user reads the table in the report file; the chat shows only a short note and the approval question. The manifest gets only the approved rows.

Write report text in ASD-STE100 (see the "Writing Standard (ASD-STE100)" section of `templates/preamble.md`). Write a recommendation as "idstack recommends that you …" or "You can …". Do not use "consider", "may", "should" or "suggest". Cite every recommendation with `[DomainCode-N] [Tier]`; uncited claims belong in *Limitations* or *Notes*, not *Findings*.

### Manifest-write rules

- **Validate JSON on read.** If malformed, report the error and stop. Never silently overwrite.
- **Own your section only.** Read the full manifest, modify only the section your skill owns, preserve everything else.
- **Update the `updated` timestamp** on every write.
- **Use `bin/idstack-manifest-merge`** for the write path. It's section-scoped, atomic (tempfile + rename), preserves foreign sections, and rejects a section name that is not in the canonical schema in `templates/manifest-schema.md` and a payload that is not a JSON object. It does not check the fields inside a section. Inline full-manifest `Edit` is the deprecated fallback.
- **Pass `--create` on every merge.** Skills run standalone, and on a missing manifest the merge exits 4 and the results are never saved. `--create` seeds a canonical manifest (through `bin/idstack-migrate --init`) and never replaces one that exists.
- **Several sections, one call.** A skill that writes more than one section repeats the `--section`/`--payload` pair in a single call, so the write is atomic. `--set project_name=<v>` writes the top-level name. For a section another skill also writes, read it, add your fields, and pass the whole merged section.

## Evidence standards

Every recommendation must cite its evidence tier:

| Tier | Meaning |
|------|---------|
| T1 | Meta-analyses, RCTs |
| T2 | Quasi-experimental with controls |
| T3 | Systematic reviews of mixed evidence |
| T4 | Observational, no comparison group |
| T5 | Expert opinion, theoretical frameworks |

Use domain codes from `evidence/references.md` (e.g., `[Alignment-14] [T1]`). Stronger evidence takes precedence when tiers conflict.

## Interaction pattern

- Ask one structured question at a time, using the `AskUserQuestion` tool. The preamble's "Interaction Conventions" section defines this protocol.
- Never batch multiple questions
- Let users work through the workflow at their own pace
- Write next-step text in the namespaced form, `/idstack:foo`. A bare `/foo` is not a command Claude Code resolves, and smoke-test fails on one.

## Testing

```bash
bin/idstack-gen-skills --dry-run  # Generated files up to date? Run this first.
./setup                           # Register your new skill with Claude Code
./test/smoke-test.sh              # Verify the install
```

Every suite below runs in CI (`.github/workflows/test.yml`) on every pull request and every push to `main`. CI starts `smoke-test.sh` and `integration-test.sh`; smoke-test runs the other suites, except `mutation-test.sh`, which CI runs in its own job. Run whichever ones your change touches locally; CI runs them all:

| Suite | Covers |
|-------|--------|
| `test/smoke-test.sh` | Install, `SKILL.md` freshness, YAML frontmatter, version agreement across `VERSION` / `plugin.json` / `CHANGELOG.md`, canonical manifest section names, `/idstack:` namespacing, resolve-snippet single source, schema migrations, `bash -n` on `setup`, `test/test-helper.sh`, `bin/lib/plugin-status.sh` and the bash scripts in `bin/` (not `idstack-timeline-log` or `package-extension.sh`), and the ASD-STE100 checks on the report templates and the extension output |
| `test/integration-test.sh` | Behavioral tests across the `bin/` scripts; also asserts the suite leaves your working tree untouched |
| `test/test-setup.sh` | `./setup` behavior — flag parsing, scope selection, failure handling, regeneration. Runs against a repo copy with a fake `$HOME` and a stub `claude` |
| `test/test-doctor.sh` | `bin/idstack-doctor` — every PROBLEM/WARNING branch and the exit contract. Runs against a repo copy with a pinned `PATH`, so "claude not found" means genuinely not found |
| `test/test-status.sh` | `bin/idstack-status`, including the `--readiness` export check. Each threshold is probed at its own boundary with the other two held passing |
| `test/test-manifest-merge.sh` | `bin/idstack-manifest-merge` |
| `test/test-plugin-status.sh` | `bin/lib/plugin-status.sh` |
| `test/test-preamble-python.sh` | The preamble's Context Recovery block (`idstack-status --context`), on the local python3 (CI runs it on 3.9 and 3.12) |
| `test/test-skill-shell-zsh.sh` | Runs real skill bash blocks in bash and in zsh (the Bash tool runs the user's shell, zsh on macOS, in a new shell for each call). Needs zsh. Runs via `smoke-test.sh` |
| `test/test-extension.sh` | The Chrome extension. Imports the shipped `extension/` modules through `test/extension-harness.mjs` (Node 20.19+ or 22.7+) and fails if a hand-copied `.cjs` twin comes back |
| `test/test-rendered-landing.js` | Renders `docs/index.html` in headless Chrome across 11 widths and asserts the rendered outcome: no horizontal scroll, 44px touch targets, breakpoint column counts, sticky nav. Catches regressions the text suite cannot see (selector lists, `@container`, nested or print-only media queries, a `<style>` inside an HTML comment). Skips loudly with no browser |
| `test/test-responsive-landing.js` | Responsive and mobile-ergonomics invariants for `docs/index.html` — fluid tokens, notch-safe gutters, breakpoint-scoped rules, touch targets. Runs on node, via `smoke-test.sh` |
| `python3 test/check-evidence-cards.py .` | Verifies that each domain row in the landing page's evidence index matches `evidence/references.md`: the study count, the per-tier counts (the tier-mix bar's `data-tiers`) and the tier range. It also fails when the number of rows differs from the number of domains |
| `python3 test/check-citation-tiers.py .` | Verifies that each `[Code-N] [Tn]` citation in the skill templates, `templates/`, README and landing page states the tier that `evidence/references.md` gives that code. `test/smoke-test.sh` runs it |
| `python3 test/test-citation-tiers.py` | `test/check-citation-tiers.py` on small test repos: codes with commas between them, a citation that a line break splits, and a blank line that ends a citation. `test/smoke-test.sh` runs it |
| `python3 test/test-report-section.py` | `bin/idstack-report-section`: `init`, `check`, `append`, `approve` and `finish`. `test/smoke-test.sh` runs it |
| `python3 test/test-ste-check.py` | `bin/idstack-ste-check`: each rule that it examines, the text that it does not examine, and the clean fixtures in `test/fixtures/ste/`. `test/smoke-test.sh` runs it |
| `python3 test/check-doc-accuracy.py .` | Checks version agreement (including `softwareVersion`), the manifest schema version, that each `bin/` path in README exists, that each one outside `bin/lib/` is executable, that each top-level `test/*.sh`, `test/*.py` and `test/*.js` file named in CLAUDE.md and CONTRIBUTING.md exists (it does not check `.mjs` files or paths in subfolders), DESIGN.md's required paths, and that removed date fields have not come back |
| `test/mutation-test.sh` | Reintroduces each known defect into a throwaway copy and asserts the guarding test fails. Add a mutation here whenever you fix a bug — it is what proves your new test would have caught it |

The CI matrix is ubuntu on Python 3.9 and 3.12, plus macOS on 3.12 for BSD `grep`/`sed`/`awk` differences. `mutation-test.sh` runs once, pinned to 3.9. Do not skip hooks or push with a red suite.

### Writing a new assertion

`test/test-helper.sh` is sourced by every bash suite that runs assertions itself and owns the counters and the assertion (`test-extension.sh` does not source it: apart from its Node version gate and its `.cjs` guard, it delegates the unit tests to node and keeps no `check()` counters; the node suites cannot source it: the two landing-page suites (`test/test-responsive-landing.js` and `test/test-rendered-landing.js`) collect their problems and report a count, and the extension unit tests use `node:assert` and stop at the first failure, except `test-disclosures.mjs`, `test-evidence-labels.mjs` and `test-ste-rules.mjs`, which collect their problems first):

```bash
. "$(dirname "$0")/test-helper.sh"

check "description"            "some-command"              # must exit 0
check "rejects an unknown section"  "$MERGE --section bogus --payload p.json"  3  # must exit 3
check "names the failing skill" "$STATUS --readiness"    0  "INCOMPLETE"
```

Arguments 3 and 4 are optional: an expected exit code, and an ERE the output must match. On failure the first five lines of output are printed locally. When `CI` is set, all of the output is printed, because CI runs most suites only through smoke-test. Do not add a private counter block (`PASS=0`, `FAIL=0`, `TOTAL=0`) or your own `check()` to a suite. For each bash suite that it lists, smoke-test asserts that the suite sources `test-helper.sh` and sets no local counters, and a mutation proves that guard works. Nine suites each had their own copy once and they drifted: two spelled it `assert`, and one swallowed failure output entirely, so CI reported a bare `FAIL` with nothing to act on.

One suite keeps a differently-shaped wrapper because its assertion is not "run a command": `check_listing` in `test/test-plugin-status.sh` feeds a `claude plugin list` listing to `plugin_is_enabled`. It is named so it cannot shadow `check`.

Then test it manually in Claude Code: `/idstack:your-skill`.

## What makes a good PR

- **Focused scope** — one skill per PR
- **Evidence-backed** — recommendations cite research, not opinions
- **Tested** — the suite passes, manual test in Claude Code works, and a bug fix ships with both the test that catches it and a mutation in `test/mutation-test.sh` that proves the test works
- **Regenerated** — `bin/idstack-gen-skills --dry-run` is clean, with generated files committed alongside the template change
- **Standalone** — skill works without a manifest (ask questions as fallback)
- **Pipeline-aware** — if upstream data exists in the manifest, use it to enrich recommendations

## Looking for something to work on?

All work is tracked in [GitHub Issues](https://github.com/savvides/idstack/issues): bugs, the feature backlog (label `backlog`), and work deferred from a review or PR. [ROADMAP.md](ROADMAP.md) is the user-facing view. Put `Closes #N` in your PR description so the issue closes when the PR merges; a bare `(#N)` in a commit subject does not close anything.

Read [DESIGN.md](DESIGN.md) before changing anything visual; it is the source of truth for the landing page. Reports and the course dashboard are plain Markdown with no styling, so `DESIGN.md` does not apply to them.
